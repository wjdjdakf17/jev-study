# 04. 어디에 쓸 수 있고, 어디까지가 한계인가

## 증명된 사용 패턴

### 스마트 if문 (AI-powered workflows)

손으로 쓰기엔 너무 브리틀하고, LLM에 맡기기엔 너무 느린 판단:

```
if (jevChoice(state, "이 사용자는 이탈 위험인가") === "high") { ... }
```

분류, 라우팅, 스코어링, 추출, 분기 — 이 레포의
confidence-gated 라우팅(`src/workflow.ts`)이 정확히 이 패턴이다.

### map-reduce — 데이터를 지능으로 훑기

공식 발표 직후 나온 커뮤니티 숫자들이 이 용도의 위력을 보여준다:

- 광고 분석: 37개 브랜드의 라이브 광고 **724개**를 40초에 분해,
  토큰 비용 **$0.09** (Matt Berman)
- 뉴스 트리아지: 그날 아침 헤드라인 **384개**를 24.9초에 읽고
  15개 브랜드가 언급할 이야기를 선별, **$0.19**.
  같은 피드를 Claude Opus로 돌리면 4개를 처리하는 데 $0.77
  (헤드라인당 약 390배 저렴)
- 반면 LLM이 강한 쪽: 생성(초안 작성), 대화, 코드. 이 영역은 그대로다.

### 실시간 제어 — LLM이 원천적으로 못 들어간 자리

- **Doom 봇**: 초당 10회 질의, 게임 상태(텍스트)를 보고 행동 선택. ~$7/시간
- **Subway Surfers**: 프레임 단위 행동 선택, 50게임 동시에, 1회 실행 $0.01 미만
- **트레이딩 봇**: 300ms 블록마다 매수/매도 결정 후 실제 온체인 주문 실행
- **브라우저 에이전트**: 매 스텝 DOM 상태에서 다음 행동을 선택.
  항공권 검색 7초 / $0.0039 (타이핑 같은 자유 입력만 소형 LLM 폴백)

70~500ms라는 응답 시간이 "AI를 UX 임계선 안에" 들여놓은 것.
이 use case군은 LLM으로는 존재 자체가 불가능했던 것들이다.

### LLM 검증 / 가드레일

LLM의 프롬프트·추론·출력을 Score/Noul로 점검:
정책 위반 여부, 프롬프트 인젝션 의심 등. "생성기 옆의 검수관" 역할.

## 공식 한계 (Jev 1.13 기준)

TypeSafe가 버전별로 유지하는 limitations 문서에 명시된 약점:

- 산술, 셈
- 날짜 비교
- 간접적인 질문 (직설적으로 물어라)
- 방해 요소가 섞인 맥락 (distracting context)
- 적대적 입력 — **보안 경계로 쓰지 마라**

처방은 일관된다: **정확한 계산은 코드에, 판단만 모델에.**
그리고 state에는 증거만 담기. 이는 LLM 워크플로 설계 원칙과 같다 —
"모델은 좁게, 코드는 넓게."

## 비판적으로 읽기

뜨거운 발표일수록 이런 질문을 붙여야 한다. 내 체크리스트:

**1. 벤치마크를 누가 만들었나**
193.6배/444.6배는 TypeSafe 자체 "workflow evals"에서 나왔다.
공식 블로그 스스로 "실제 환경에서는 이보다 낮은 쪽(end)에 있을 것"이라고
못 박았다. 참조 답으로 GPT-6 Astra와 Fable 5.1의 평균을 쓴 것도
OpenAI/Anthropic 계열 모델에 유리한 편향일 수 있다(본인들도 인정).
웍플로 제작자도 자사 팀이라 "선택 편향" 여지를 스스로 인정한다.

**2. 셀프 리포트 데모들**
$0.09 광고 분석, $0.19 뉴스 트리아지 등은 커뮤니티 크리에이터의
자체 측정이고 프로토타입이다. 품질(정확도) 검증은 대부분 눈으로 봤다.

**3. "환각 없음"의 정확한 의미**
"타입 에러가 구조적으로 불가능"하다는 건 수학적 주장이 맞다.
하지만 "틀린 답을 고르지 않는다"는 뜻이 아니다.
structured ≠ correct — 이 구분을 놓치면 마케팅에 당한다.

**4. 보정의 독립 검증 부재**
RLCD로 보정이 좋아졌다는 건 벤더 주장이다. 검증하려면
내 트래픽으로 직접: 신뢰도 버킷(reliability diagram)을 그려보고
(→ `src/calibration.ts`), 80% 구간의 실제 적중률이 80%인지 확인한다.
공식 문서도 "자체 평가는 여전히 필요하다"고 못 박는다.

**5. 지속 가능성**
$0.042/MTok 가격이 보조금인지 아닌지는 "장기적으로 증명할 것"
(본인들 말). 초기 할인 가능성을 배제할 수 없다.

## 그래도 남는 것

회의적으로 다 걷어내도, 아래는 부정하기 어렵다고 본다:

1. **인터페이스의 진화**: "문자열 생성 → 타입화된 결정"이라는
   API 설계 자체가 소프트웨어와 모델의 접점을 다시 생각하게 한다
2. **병렬 샘플링의 증명**: 생성을 포기하면 속도/비용 구조가
   자릿수 단위로 바뀔 수 있다는 실증
3. **confidence-first 설계**: "판단에는 확률이 붙어야 하고,
   확률을 소비하는 건 코드다" — 이 패턴은 Jev 없이도 지금 당장
   (LLM structured output으로) 적용할 수 있는 교훈이다
