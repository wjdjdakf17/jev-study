# 02. 작동 방식 — state, 질문 3종, 병렬 샘플링

Jev의 API는 "대화"가 아니라 **"질의"**다. 요청 하나의 구조:

```
┌─────────────────────────────────────────────────────┐
│  state      판단의 재료가 되는 비정형 상태             │
│             (예: 티켓 제목+본문, 게임 상태, DOM 스냅샷) │
├─────────────────────────────────────────────────────┤
│  questions  질문 배열 — 서로 독립적인 판단들을 병렬로    │
│             · Choice  : 선택지 중 하나                  │
│             · Score   : 루브릭 척도 위의 위치            │
│             · Noul    : yes/no 명제의 확률              │
├─────────────────────────────────────────────────────┤
│  decisions  질문 key → { 값 + 확률 분포 + confidence }  │
│             파싱 불필요. 타입이 곧 계약.                │
└─────────────────────────────────────────────────────┘
```

## state — "대화"가 아니라 "프로그램 상태"

LLM API가 순차적인 메시지 배열을 받는 것과 대비되는 설계.
Jev는 **구조화된 프로그램 상태**를 입력으로 강조한다.

실무적 함의: 판단에 필요한 증거만 담아야 한다.
갖고 있는 정보를 전부 던지는 건 오히려 해가 된다 —
공식 limitations 문서에도 "방해 요소(distracting context)에 약하다"가
명시되어 있다. state 큐레이션이 곧 프롬프트 엔지니어링이다.

## 질문 프리미티브 3종

### 1. Choice — 선택지 중 하나를 골라라

```ts
{
  kind: "choice",
  key: "route",
  question: "이 티켓을 처리할 팀은?",
  options: ["billing", "technical", "account"],  // 최대 255개
}
```

응답: 선택된 옵션 + **전체 옵션에 걸친 확률 분포** + confidence.

"billing 92% · technical 5% · account 3%"처럼 전체 분포를 주는 게
포인트다. 당첨 라벨만 보면 숨는 애매함이 분포에는 드러난다.

255개가 넘는 선택지(Wikiracing처럼 링크 수천 개)에는
**2단계 질의**를 쓴다고 한다: 1단계에서 점수 매기기, 2단계에서
명시적 선택. 큰 cardinality에서도 타입 안전성을 유지하는 방식.

### 2. Score — 루브릭 위에서 평가해라

```ts
{
  kind: "score",
  key: "severity",
  question: "보고된 문제의 심각도는?",
  levels: [
    { label: "cosmetic", description: "치장 수준. 기능 영향 없음." },
    { label: "degraded", description: "기능이 망가졌지만 우회로가 있음." },
    { label: "blocking", description: "업무가 완전히 막힘. 즉시 대응." },
  ],
}
```

단순 "1~10점"과의 차이: 각 단계에 **설명을 붙인다.**
점수의 의미를 모델의 해석에 맡기지 않고 스펙으로 못 박는 것.
응답 역시 단계별 확률 분포 + confidence.

### 3. Noul — 명제의 참일 확률만

```ts
{
  kind: "noul",
  key: "wantsRefund",
  proposition: "사용자가 환불을 요청하고 있다",
}
```

응답: `P(yes) = 0.87` 하나. Choice/Score와 달리
confidence 필드가 없다 — **확률 자체가 애플리케이션이 쓸 신호**다.

## 병렬 샘플링 — 속도의 비밀

LLM은 토큰을 하나씩, 앞 토큰을 조건으로 순차 생성한다(자기회귀).
출력이 길수록 시간이 선형으로 늘어난다.

Jev는 출력이 애초에 "정의된 구조 안의 값"이라
**전체 출력을 한 번의 병렬 패스로 뽑는다.** 질문 여러 개도
같은 state 위에서 동시에 처리된다.

결과:

| | 프론티어 LLM | Jev |
| --- | --- | --- |
| end-to-end 응답 | 3초 ~ 329초 | **70ms ~ 500ms** |
| 입력 토큰 비용 | $0.20 ~ $10 / MTok | **$0.042 / MTok** |
| 출력 토큰 비용 | 입력의 ~5배 | **무료(측정 불가 수준)** |

공식 주장은 "같은 프론티어 지능 기준 40~200배 빠르고 40~400배 저렴".
홈페이지의 193.6배 빠름 / 444.6배 저렴이라는 숫자는 자체
"workflow evals"에서 나왔다(측정 방법과 논란은 [04](04-use-cases-limits.md)에서).

덧붙이는 정황 증거: 제3자 독립 구현인
[jevlike](06-jevlike-open-implementation.md)도 "선택지 8개, 한 패스"가
소형 디코더가 400토큰 생성하는 것보다 **약 100배 빨랐다**고 보고한다.
원패스 구조의 속도 이점은 벤더 주장이 아니라 구조의 성질로 보인다.

## confidence와 calibration — 이 모델의 철학

두 개를 구분해서 이해해야 한다.

**confidence (응답 필드)**: Choice/Score 응답에 붙는 요약치.
확률 분포에서 **계산해서 도출**된 값이지, 모델이 "자신 있어요"라고
말하는 문장이 아니다. 분포가 몰려 있으면 높고, 비등하면 낮다.

**calibration (모델의 성질)**: "80%라고 말한 예측이 실제로 80%
일어나는가"라는 통계적 성질. RLCD 학습법이 직접 최적화하는 대상.

공식 발표에서 내가 가장 인상적인 문장:

> "어떤 일을 95% 잘하는 모델이, 나머지 5%가 언제인지 말하지
> 못하면, 그 일은 자동화할 수 없다."

LLM에 "confidence를 알려줘"라고 하면 대개 과신하고 일관성이 없다.
Jev는 confidence가 모든 응답에 필수로 붙고, 높을수록 정확하도록
학습됐다는 것. 이것이 "확률을 소비하는 if문"
(= confidence-gated routing, `src/workflow.ts` 참고)을 가능하게 한다.

보정을 직접 측정해 보고 싶으면 `src/calibration.ts`의
Brier score와 신뢰도 버킷을 보라. 실제 평가에 바로 쓸 수 있는
표준 도구들이고, 테스트도 작성해 두었다.
