# 03. LLM과의 비교 — 무엇을 포기하고 무엇을 얻었나

공식 발표의 비교표를 축약하며 내 주석을 달았다.

## 전체 비교

| 축 | 기존 LLM | System One (Jev) | 내 주석 |
| --- | --- | --- | --- |
| 학습법 | RLHF / RLVR | **RLCD** | 최적화 대상 자체가 다름 (아래) |
| 입력 | 비정형 데이터, **순차 메시지** 강조 | 비정형 데이터, **구조화된 상태** 강조 | 같은 텍스트라도 "대화" vs "상태" |
| 출력 | **문자열** — 자유롭지만 파싱+검증 필요, 탈선 가능 | **타입화된 값** — 구조가 미리 정의됨, 타입 에러 불가능 | 문자열의 자유 = 힘이자 리스크 |
| 샘플링 | 순차 (토큰 하나씩) | **병렬** (출력 전체를 한 번에) | 속도/비용 차이의 근원 |
| 비용 | 입력 $0.20~10/MTok, 출력은 ~5배 | 입력 $0.042/MTok, **출력 무료** | "출력 무료"는 병렬 샘플링의 직접적 결과 |
| 속도 | 3~329초 | **70~500ms** | 실시간 사용(로봇, 게임, UX)의 문턱을 넘음 |
| confidence | 요청해도 과신하고 불일치 | 모든 응답에 필수 + 보정됨 | 자동화의 성패를 가르는 축 |
| 용도 | 휴먼 인 더 루프, 검증 가능 문제, 데모 | **스마트 if문**, map-reduce, 실시간, 검증/가드레일 | 경쟁이 아니라 분업 (아래) |

## 학습법: RLHF / RLVR / RLCD

세 벌의 목표 함수가 세 벌의 모델을 만들었다는 관점이 깔끔하다.

- **RLHF** (Human Feedback): 인간 평가자가 *선호하는* 답변을 만들도록 최적화. 선호 = 잘 쓴 글, 매끄러운 대화. 자동화에 필요한 건 "정직한 불확실성"인데, 선호 최적화는 오히려 확신에 찬 서술을 장려하는 방향으로 기운다.
- **RLVR** (Verifiable Rewards): 정답을 프로그램으로 검증할 수 있는 문제(수학, 코드)에 최적화. 강력하지만 검증 가능한 도메인에 갇힌다.
- **RLCD** (Calibrated Decisions): "인식적으로 정직한 확률이 붙은 결정"을 직접 최적화. 보정(calibration)이 부수 효과가 아니라 목적 함수 자체.

## "문자열을 포기한다"는 것의 무게

LLM의 힘은 문자열이 **무엇이든 될 수 있다**는 데 있다.
채팅 답변, 코드, 시, 그리고 환각까지. 범용성의 대가:

1. **파싱 레이어**: 코드에서 쓰려면 JSON 파싱 + 스키마 검증 + 재시도
2. **탈선 리스크**: 언제나 "레일을 벗어날" 가능성이 남는다
3. **깊은 의존성 문제**: 에이전트에서 환각 도구 호출 하나는 성가시지만,
   레이턴시 보장이 있는 시스템에서, 의존성 체인 몇 층 아래 파묻힌
   타입 에러 하나는 치명적이다 (공식 발표의 표현)

Jev는 가능한 출력을 질의에 미리 정의함으로써 이 셋을 원천 제거한다.
"문자열을 포기하면 오히려 초능력이 생긴다"는 게 발표의 뼈대.

다만 냉정하게: **structured ≠ correct.**
정의된 선택지 "안에서" 틀린 답을 고르는 건 여전히 틀린 답이다.
타입 안전성은 실패의 **모양**을 좁힐 뿐, 판단 자체의 품질은
별도로 평가해야 한다. (실제로 Requesty 분석도 이 점을 짚는다.)

## 경쟁이 아니라 분업

실무 그림은 이렇게 그려진다:

```
                    ┌──────────────┐
  티켓 입력 ──▶ Jev: │ 라우팅/심각도/ │ ──▶ if문 (confidence 게이트)
                    │ 환불 여부 판단  │        │
                    └──────────────┘   ┌──────┴──────┐
                                  자동 │              │ 애매
                                  처리 ▼              ▼
                              LLM: 답변 초안     사람: 검토
```

- **판단(judgment)** → Jev: 좁고, 빠르고, 확률이 붙는 결정
- **정책(policy)** → 코드: 임계값, 게이트, 분기 — 감사 가능해야 하니까
- **생성(generation)** → LLM: 최종 답변 초안, 코드, 글

한 워크플로우에 셋이 섞이는 게 기본이 될 거라는 전망.
`src/workflow.ts`가 바로 이 그림의 축소판이다.

## 그래서 "작은 LLM"과 뭐가 다른가

"그냥 structured output 쓰는 소형 LLM 아니야?"라는 질문은
정당하다 (HN 토론에서도 최다 공감 질문). TypeSafe의 답변 요지:

1. structured output은 LLM에 **양심검사대**를 붙이는 것 — 생성 방식은
   여전히 자기회귀라 속도/비용 구조가 그대로고, 스키마 위반 위험이
   확률적으로 남는다
2. Jev는 스키마 일치가 **구조적으로 보장**되고(경험치가 아니라 수학),
   샘플링 방식 자체가 병렬이라 비용 구조가 다르다
3. 학습 목표(RLCD)가 처음부터 결정+보정이었다

진위는 벤치마크와 시간이 판정할 문제고, 지금은
"인터페이스 철학의 차이"로 이해해 두는 게 정확하다.
